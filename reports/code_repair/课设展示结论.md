# 代码任务：反馈质量、停止时机与测试盲区

2026-10-26。新增真实多轮实验已经完成：**164 题、两个 Qwen 模型、5,576 份实际回答及对应评分**。这一章可以接在已有“独立重复采样”之后，回答三个课堂问题：给代码一个反例有多大用？是否应该一直修改？测试没发现的错误会怎样？

## 一、先讲清楚我们做了什么

原 CodePromptEval 的五次回答是五次独立生成。这次增加 HumanEval+ Mini v0.1.10 的自包含函数题，模型能够看到自己的上一版代码，并获得真实的本地测试反馈。

每个模型、每题先生成一份共同初稿，再分成四组。生成温度为 0.2，输出上限 2,048 Token；Qwen3 关闭思考。四组各获得四次后续生成机会，连同初稿形成五个版本。实际请求为每个模型每题 `1 + 4×4 = 17` 份，初稿在四组中复用。

| 方案 | 下一次请求看到什么 |
|---|---|
| 独立重抽 | 原题；不看前一次回答和测试结果 |
| 无反馈自查 | 原题及本组完整历史；要求检查正确性、修正问题、保留正确实现 |
| 状态反馈 | 与自查相同，再给真实诊断 `PASS / FAIL` |
| 具体用例反馈 | 与状态反馈相同，失败时再给第一个失败输入、期望输出、实际输出或异常 |

模型只接收 `base_input` 的诊断结果；`plus_input` 只在本地评测。共有 1,570 条 base 和 1,107 条 plus，其中 49 条输入重叠，另有 1,058 个不同于 base 的新输入。完整通过表示一份程序同时通过两套测试。所有统计按题目计算，95% 区间使用 5,000 次配对 bootstrap。

这个补实验与原来的 194 道 CodePromptEval 题分别汇总，继续放在同一个仓库。

研究设计参考 [Self-Debugging](https://arxiv.org/abs/2304.05128)、[Is Self-Repair a Silver Bullet for Code Generation?](https://arxiv.org/abs/2306.09896) 和 [ACL 2025 的自生成测试调试研究](https://aclanthology.org/2025.acl-long.881/)，重点检查执行反馈、调用成本和额外测试，而非只展示修复成功的案例。

## 二、结论一：具体反例显著增强 Qwen3 的修复能力，单给 FAIL 的帮助小得多

**课程类别：多维，涉及反馈方式 × 轮次 × 完整通过率；模型作为分面。**

### 铺垫与原始预期

一个直观预期是：告诉模型代码错了，再给几次检查机会，它应该能够修正。四组对照可以进一步看清，只有“错了”这个信号是否足够，具体执行反例还能带来多少收益。

### 一对真实代码：把题目中已有的边界条件变成执行证据

`HumanEval/102` 要求返回闭区间 `[x, y]` 内最大的偶数，区间无有效结果时返回 `-1`。题目已给出 `choose_num(13, 12) = -1`。

Qwen3 初稿却额外交换端点：

```python
if x > y:
    x, y = y, x
```

诊断实际返回：输入 `[13, 12]`，期望 `-1`，代码输出 `12`。第一次收到具体反馈后，模型仍保留旧代码；第二次收到反馈后改为：

```python
if x > y:
    return -1
```

修改后同时通过诊断与 plus 测试。这条轨迹显示，反例把“哪条额外假设错了”直接暴露了出来；它也显示修复有时需要不止一轮。

### 总体证据

Qwen3 的初稿为 **126/164，76.83%**。固定生成到第五版后：

| 方案 | 完整通过 | 初始诊断失败的 30 题中修好 |
|---|---:|---:|
| 独立重抽 | 123/164，75.00% | 3/30，10.00% |
| 无反馈自查 | 129/164，78.66% | 3/30，10.00% |
| 状态反馈 | 130/164，79.27% | 4/30，13.33% |
| 具体用例反馈 | **141/164，85.98%** | **15/30，50.00%** |

具体用例反馈相对无反馈自查提高 **7.32 个百分点，95% CI [3.05, 12.20]**；相对状态反馈提高 **6.71 个百分点，[3.05, 10.98]**。

在 Qwen2.5 上，四组第五版分别为 128、131、130、134 题，具体反馈的增幅较小。两模型等权汇总、同题两模型共同重抽时，具体用例反馈相对自查提高 **4.57 个百分点，[2.13, 7.32]**，相对状态反馈提高 **4.57 个百分点，[1.83, 7.62]**。

**解释：**失败输入、期望和实际输出能指出代码违背规格的具体位置。只给 FAIL 仍要求模型自行定位问题；保留历史并反复自查，也可能重复原来的错误假设。

**适用范围：**本次两款 Qwen、HumanEval+ Mini、初稿加四轮；最清晰的模型级证据来自 Qwen3。这里比较的是最终交付版本，独立重抽的“曾经有一版成功”和“保留首次诊断通过”另列分析。

主图：[五个实测版本 SVG](full/01-five-rounds.svg)。Qwen3 具体反馈的五点为 **126 → 131 → 136 → 137 → 141**；第五版比第四版净多 4 题，当前曲线仍有后续收益。固定该模型和反馈方式后，轮次与通过率构成低维展示图。

## 三、结论二：跑满五轮的多数 Token 可以省下，保留首次诊断通过的版本更有效率

**课程类别：多维，涉及候选选择规则 × Token × 完整通过率，分模型和方案展示。**

### 铺垫与问题

前一条比较五轮生成后的代码质量。真实使用时，还需要决定交付哪一版：取第五版，还是一旦诊断通过就保留？我们用保存的真实轨迹回放第二种规则，只使用诊断结果决定何时停止，plus 结果不参与选择。

### 总体证据

在 **全部 8 个模型×方案条件** 中，保留首次诊断通过的版本，其完整通过题数均不低于第五版；平均调用数降至 **1.50～1.67 次**，Token 比固定跑满五轮少 **64.83%～76.72%**。

| 模型、方案 | 第五版通过 | 首次诊断通过即保留 | 五轮 Token / 题 | 停止回放 Token / 题 |
|---|---:|---:|---:|---:|
| Qwen2.5 独立重抽 | 128/164 | **140/164** | 2,188 | **708** |
| Qwen2.5 无反馈自查 | 131/164 | **135/164** | 5,685 | **1,323** |
| Qwen3 状态反馈 | 130/164 | 130/164 | 4,557 | **1,193** |
| Qwen3 具体用例反馈 | 141/164 | 141/164 | 4,880 | **1,334** |

Qwen3 具体反馈保留了全部 141 题的成功，同时回放 Token 减少 **72.67%**。Qwen2.5 自查组则同时出现输出成本下降和交付成功数增加。

### 解释与实际版本变化

后续生成既可能修复，也可能覆盖已经正确的版本。Qwen2.5 自查组最终修好 3 道初错题，也改坏 4 道初对题；独立重抽第五份相对初稿增加 4 道成功，同时丢掉 8 道原有成功。保留通过诊断的版本可以避免这部分覆盖损失。

另一方面，完整历史会重复进入输入预算：Qwen3 自查五轮共约 4,425 Token，其中输入/历史约 3,379。即使每轮输出不长，反复携带历史也会积累成本。

**适用范围：**这是对实测轨迹进行的停止规则回放，实验实际仍采满五轮。规则最多用五次调用，失败时保留最后一版，诊断通过时保留首次通过版。

候选选择会影响方案排名：按首次诊断通过交付时，Qwen2.5 独立重抽为 140/164，具体反馈为 136/164；Qwen3 则为 130/164 与 141/164。具体反馈相对自查的优势在两模型汇总的停止回放下仍为 **+3.96 个百分点，[1.83, 6.40]**。这两组证据分别说明反馈对修改的作用，以及版本选择对交付的作用。

主图：[停止规则的成本与表现 SVG](full/04-stopping-policy.svg)；[输入与输出 Token SVG](full/03-token-cost.svg)。

## 四、结论三：测试盲区会延续到多轮修复之后

**课程类别：异常与局限，解释测试驱动闭环的覆盖边界。**

### 铺垫与预期

通过现有测试，容易让人相信程序已经完成。但测试反馈只能暴露它检查过的问题。我们在不提供 plus 结果的情况下，检查最初已经通过诊断、却没有通过额外评测的程序。

### 总体证据

- Qwen2.5 有 **7** 个这样的初始条件，Qwen3 有 **8** 个，共 **15 个模型×题目条件**。
- 在四种方案的第五版中，这 **15 个条件全部仍未完整通过**。
- Qwen3 具体用例反馈能修好 **15/30 个诊断可见错误**，但对 **8 个起初漏测的错误，最终修好 0 个**。

“全部仍错”指最终版本。Qwen3 自查中有一个条件曾在中途通过，后来又回退；完整逐轮结果保留在表中。

### 同一道日期校验题，两种真实盲区

`HumanEval/124` 的规则规定二月最多 29 天，并要求严格的 `mm-dd-yyyy` 格式。

**Qwen2.5** 使用 `datetime.strptime`，引入了题目未要求的闰年检查：`02-29-2021` 按题目规则应返回 `True`，模型代码却返回 `False`。

**Qwen3** 使用 `re.match` 检查日期前缀：`06-04-2020\n` 仍被接受，严格格式测试应返回 `False`。

两份代码都通过原诊断测试。反馈因此持续给出 PASS，这两个边界问题没有形成针对性的纠错信号。

**解释：**测试覆盖决定了闭环能指出哪类错误。增加对话轮次和已有测试的 PASS 信号，未能稳定补上这些漏测条件。代码任务的这一条发现可以与问答任务的答案提取局限并列展示，讲清“分数来自哪条检查链”。

**适用范围：**15 个条件是在初稿上固定识别的，比较四组最终版本；不把四组复用的同一初稿计算成 60 个独立问题。额外评测仍是 HumanEval+ Mini 提供的有限测试集。

## 五、课设中怎样讲这一章

建议用三页主发现加一页案例：

1. **生成之后需要什么反馈？** 用逆序区间的实际代码和五点曲线，展示具体反例的作用。
2. **修到什么时候？** 用停止规则的成本—表现图，展示历史成本和版本覆盖损失。
3. **测试通过以后还缺什么？** 用日期校验的两份代码，展示共同的漏测边界。

这三条补强原来偏弱的代码场景发现。课程基础五条继续与数学、文档位置共同组织；本章明确提供两条多维候选和一条异常发现，轮次曲线作为低维支撑图，不另行重复计算同一条主发现。
